# 3. ent の全体像とコード生成

> **この章でわかること**
> スキーマ → entc → 生成コードという流れ。生成されるものの種類と役割。Client と Builder という 2 つの主役。題材アプリの構成、`entc.go` の設定と、そこで有効にしている機能フラグ。`make gen` の正体。既存 DB からスキーマを取り込むという選択肢。

この章を読み終えると、ent を使ったプロジェクトの `ent/` ディレクトリを開いたときに「どこに何があるか」が分かるようになります。

---

## 3.1 全体の流れ

ent を使った開発は、次の 3 段階で回ります。

```
① スキーマを書く      ent/schema/*.go
        ↓
② コードを生成する    entc（make gen）
        ↓
③ 生成コードを使う    ent.Client, ent.CollectionQuery …
```

Prisma と同じ形です。

| 段階 | Prisma | ent |
| --- | --- | --- |
| ① | `schema.prisma` | `ent/schema/*.go` |
| ② | `prisma generate` | `entc`（題材アプリは `make gen`） |
| ③ | `@prisma/client` | `ent/` 配下の生成コード |

人間が触るのは ① だけです。② で生成されたコードは**手で編集しません**。生成されたファイルの先頭には、必ずこう書かれています。

```go
// Code generated by ent, DO NOT EDIT.
```

題材アプリのチームの規約でも「`ent/` 直下の生成物は手編集禁止」と明記しています。

## 3.2 題材アプリの構成とスキーマの場所

本書の題材アプリは、次のような構成になっています。以降の章でパスが出てきたら、この図を基準にしてください。

```
app/
├── ent/
│   ├── schema/         ← スキーマ（人間が書く）
│   ├── common/         ← Mixin など（人間が書く）
│   ├── entc.go         ← 生成の設定（人間が書く）
│   ├── migrate/main.go ← 差分生成（人間が書く。第 12 章）
│   ├── migrate/migrations/ ← マイグレーション SQL
│   └── それ以外        ← すべて生成物
├── graph/              ← GraphQL の resolver
├── usecase/            ← ユースケース
├── domain/models/      ← ドメインモデル
├── domain/ports/       ← Repository などのインターフェース
├── infrastructure/db/repository/ ← Repository の実装
├── store/              ← DB 接続
├── test/factory/       ← テストデータの factory
├── tools/              ← 自作 lint
└── generate.go
```

`ent/` の中に「人間が書くもの」と「生成物」が同居しています。最初は混乱しますが、**`schema/` と `common/` と数個の設定ファイル以外は全部生成物**と覚えておけば十分です。

スキーマ 1 つは、こういう形をしています。

```go
// ent/schema/collection.go（抜粋）
type Collection struct {
  ent.Schema
}

func (Collection) Fields() []ent.Field { ... }
func (Collection) Edges() []ent.Edge { ... }
func (Collection) Indexes() []ent.Index { ... }
func (Collection) Annotations() []schema.Annotation { ... }
```

`ent.Schema` を埋め込んだ struct に、必要なメソッドを生やしていきます（第 2 章 2.2）。

| メソッド | 何を書くか | 詳しくは |
| --- | --- | --- |
| `Fields()` | 列 | 第 4 章 |
| `Edges()` | 関係 | 第 5 章 |
| `Indexes()` | インデックス | 第 6 章 |
| `Annotations()` | DB・GraphQL 向けの追加設定 | 第 6・13 章 |
| `Mixin()` | 共通部品の取り込み | 第 6・11 章 |

`ent.Schema` はほかに `Hooks()`、`Interceptors()`、`Policy()` も持っていますが、題材アプリのスキーマで直接書いているのは上の 5 つだけです。Hook と Interceptor は Mixin 経由で使っています（第 11 章）。

## 3.3 何が生成されるか

`ent/` を開くと大量のファイルとディレクトリが並んでいます。テーブルが 100 を超える規模なら、`ent/` 直下の Go ファイルは数百にのぼります。

種類で分けると、実はそれほど多くありません。

### エンティティごとに生成されるもの

`Collection` スキーマ 1 つから、次のファイルができます。

```
ent/
├── collection.go         ← エンティティの struct
├── collection_create.go  ← 作成用 Builder
├── collection_update.go  ← 更新用 Builder
├── collection_delete.go  ← 削除用 Builder
├── collection_query.go   ← 取得用 Builder
└── collection/
    ├── collection.go     ← 列名の定数・並び替え
    └── where.go        ← 述語（検索条件）
```

| ファイル | 中身 |
| --- | --- |
| `collection.go` | `type Collection struct`（取得結果の入れ物） |
| `collection_query.go` | `CollectionQuery`（`Where`, `All`, `WithXxx`…） |
| `collection_create.go` | `CollectionCreate`（`SetTitle`, `Save`…） |
| `collection_update.go` | `CollectionUpdate` / `CollectionUpdateOne` |
| `collection_delete.go` | `CollectionDelete` / `CollectionDeleteOne` |
| `collection/where.go` | `TitleEQ`, `HasArticles`… |
| `collection/collection.go` | `FieldTitle` などの定数、`ByTitle` |

`collection/` パッケージ（小文字）と `ent.Collection` 型（大文字）は別物です。

- `ent.Collection` … データの入れ物
- `collection.TitleEQ(...)` … 検索条件を作る関数

### 全体で 1 つだけ生成されるもの

| ファイル・ディレクトリ | 役割 |
| --- | --- |
| `client.go` | `ent.Client` と各エンティティの `XxxClient` |
| `tx.go` | トランザクション `ent.Tx` |
| `mutation.go` | 全エンティティの `XxxMutation`（第 8 章） |
| `ent.go` | 共通の型、エラー型、`Asc`/`Desc` など |
| `predicate/` | 述語の型定義 |
| `hook/` | Hook を書くためのヘルパー |
| `migrate/` | DB スキーマ定義（`schema.go` など） |
| `runtime/` | スキーマの Hook・デフォルト値の登録 |
| `enttest/` | テスト用のクライアント生成 |

ここまでが ent 本体の生成物です。題材アプリでは、さらに機能フラグと拡張によって生成物が増えています（3.6, 3.7）。

### runtime パッケージ

`runtime/` だけは少し特殊なので補足します。

スキーマに Hook を書くと、スキーマパッケージと生成された `ent` パッケージが**お互いを import し合う**（循環 import）ことがあります。題材アプリの論理削除 Mixin も `example.com/app/ent/hook` を import しています。

これを避けるため、ent は Hook などの登録処理を `ent/runtime` という別パッケージに書き出します。公式ドキュメントは、このパッケージを**必ず import するように**と書いています（`doc/md/hooks.md`）。

```go
// cmd/graphql/main.go
import _ "example.com/app/ent/runtime"
```

`_` は「使わないけど読み込む（初期化処理だけ走らせる）」という import です。JS の `import "./polyfill"` と同じです。

**これを忘れると、Hook やデフォルト値の関数が登録されません。** 生成コードはそれを検知して、`ent: uninitialized hook (forgotten import ent/runtime?)` のようなエラーを返します（第 11 章）。新しいエントリーポイントを作るときは要注意です。

## 3.4 主役は 2 つ — Client と Builder

生成コードは膨大ですが、使う側から見える主役は 2 つだけです。

### Client — 入り口

```go
client.Collection // *ent.CollectionClient
client.Article    // *ent.ArticleClient
```

`ent.Client` はエンティティごとの `XxxClient` を束ねたものです。Prisma の `prisma.collection` と同じ位置付けです。

`XxxClient` には操作の入り口となるメソッドが並びます（`ent/client.go`）。

| メソッド | 返すもの |
| --- | --- |
| `Query()` | `*CollectionQuery` |
| `Create()` | `*CollectionCreate` |
| `Update()` / `UpdateOneID(id)` | `*CollectionUpdate(One)` |
| `Delete()` / `DeleteOneID(id)` | `*CollectionDelete(One)` |
| `Get(ctx, id)` | `*Collection`（即実行） |

### Builder — 組み立てて、最後に実行

`Get` 以外は、すぐには何も実行しません。**Builder（組み立て役）**を返します。

```go
client.Collection.Query().          // Builder を作る
  Where(collection.TitleEQ("foo")). // 条件を足す
  Order(collection.ByTitle()).      // 並び順を足す
  All(ctx)                         // ここで初めて SQL が飛ぶ
```

`ctx` を受け取るメソッドが**実行**、受け取らないメソッドが**組み立て**です。この見分け方は覚えておくと便利です。

| 組み立て（ctx なし） | 実行（ctx あり） |
| --- | --- |
| `Where`, `Order`, `Limit` | `All`, `Only`, `First` |
| `WithXxx`, `Select` | `Count`, `Exist`, `IDs` |
| `SetXxx`, `ClearXxx` | `Save`, `Exec` |

Knex や Kysely のクエリビルダを使ったことがあれば、同じ感覚です。Prisma のように「1 回の関数呼び出しにオブジェクトを渡す」のではなく、**チェーンで積み上げてから最後に実行する**スタイルです。

読み（第 7 章）と書き（第 8 章）の詳細は後で扱います。

## 3.5 entc — 生成の設定ファイル

生成を担うのは `entc`（ent codegen）というパッケージです。最小構成なら CLI 一発で済みますが、題材アプリは entgql 拡張を差し込むため、**Go のプログラムとして生成処理を書いて**います（機能フラグだけなら CLI の `--feature` でも指定できます）。

```go
// ent/entc.go（抜粋・簡略化）
//go:build ignore

func main() {
  ex, err := entgql.NewExtension(
    entgql.WithConfigPath("./gqlgen.yml"),
    entgql.WithSchemaPath("./graphqls/ent.graphqls"),
    entgql.WithSchemaGenerator(),
    entgql.WithWhereInputs(true),
    entgql.WithSchemaHook(/* node/nodes を除く */),
  )
  // ...
  err = entc.Generate(
    "./ent/schema",
    &gen.Config{},
    entc.Extensions(ex),
    entc.FeatureNames(
      "privacy",
      "intercept",
      "schema/snapshot",
      "sql/modifier",
      "sql/upsert",
      "sql/versioned-migration",
      "sql/lock",
      "sql/execquery",
    ),
  )
}
```

やっていることは 3 つです。

1. `./ent/schema` のスキーマを読む
2. **entgql 拡張**を差し込む（3.7）
3. **機能フラグ**を有効にする（3.6）

`//go:build ignore` が付いているので、アプリ本体のビルドには含まれません（第 2 章 2.10）。

## 3.6 機能フラグ（FeatureNames）

ent の生成コードには、**オプトインで有効にする機能**があります。デフォルトでは生成されず、フラグを指定したときだけ対応するコードが増えます。

題材アプリで有効にしているフラグと、その意味はこうです（説明は `entc/gen/feature.go` と `doc/md/features.md` より）。

| フラグ | 何ができるようになるか | 詳しくは |
| --- | --- | --- |
| `privacy` | 読み書きの認可ポリシー層 | 第 11 章 |
| `intercept` | Interceptor を書くためのヘルパー（`ent/intercept`） | 第 11 章 |
| `schema/snapshot` | スキーマのスナップショットを保存し、マージ時の衝突を自動解決しやすくする | 本節・第 12 章 |
| `sql/modifier` | `Modify` で SQL を直接いじる | 第 9 章 |
| `sql/upsert` | `ON DUPLICATE KEY UPDATE` による upsert | 第 8 章 |
| `sql/versioned-migration` | マイグレーションファイルの生成 | 第 12 章 |
| `sql/lock` | `SELECT ... FOR UPDATE` | 第 9 章 |
| `sql/execquery` | 生 SQL の実行（`ExecContext` / `QueryContext`） | 第 9 章 |

フラグを有効にすると生成物が増えます。たとえば `privacy` で `ent/privacy/`、`intercept` で `ent/intercept/` ができます。

### schema/snapshot

ここで概要を説明しておきます。マイグレーションとは無関係であることは、第 12 章 12.11 でも触れます。

ent の生成コードは巨大なので、2 人が別々にスキーマを変えてマージすると、生成物が衝突して**ビルドが通らなくなる**ことがあります。生成ツール自体が、壊れた生成コードを import しているせいで動かない、という鶏と卵の状態です。

`schema/snapshot` を有効にすると、最新のスキーマ情報が `ent/internal/schema.go` にスナップショットとして保存されます。entc はスキーマが読めないとき、これを使って生成をやり直せます（背景は ent の issue #852）。

題材アプリでは、生成の要否をハッシュで判定するスクリプト（`scripts/gen.sh`。3.8）の対象から、このファイルを外しています。`ent/internal/schema.go` はどこからも import されないうえ、entc を回すたびに中身が変わるからです。**普段は意識しなくてよいファイル**だと分かります。

## 3.7 entgql 拡張 — GraphQL も一緒に生成する

`entc.Extensions(ex)` で差し込んでいる `entgql` は、ent の公式拡張（`entgo.io/contrib/entgql`）です。

これにより、ent のスキーマから**GraphQL 用のコードとスキーマ**も生成されます。

| 生成物 | 役割 |
| --- | --- |
| `graphqls/ent.graphqls` | GraphQL スキーマ（テーブル数に比例して数万行になることも） |
| `ent/gql_pagination.go` | Relay 形式のページネーション |
| `ent/gql_collection.go` | 要求フィールドに応じた eager loading |
| `ent/gql_where_input.go` | 絞り込み用の `XxxWhereInput` |
| `ent/gql_node.go` | Relay の Node インターフェース |
| `ent/gql_edge.go` | エッジを GraphQL フィールドとして解決するメソッド |
| `ent/gql_transaction.go` | `OpenTx`（tx と、tx 用クライアントを載せた ctx を返す）。題材アプリでは `RunInTransaction` が使う（第 9・13 章） |

設定のポイントだけ押さえておきます。

- `WithSchemaGenerator()` … `ent.graphqls` を**自動生成**する
- `WithWhereInputs(true)` … 絞り込み入力型を生成する
- `WithSchemaHook(...)` … 生成された GraphQL スキーマから `Query.node` / `Query.nodes` を取り除く

最後の点には、`entc.go` にコメントで理由を書いています。要約すると、**`ent_types` テーブルが無いので node / nodes は正しく動かず、残しても匿名で全型に ID で到達できる口になるだけなので外している**、ということです。

`ent.graphqls` は生成物なので手で編集してはいけません。GraphQL の型を変えたいときは、ent のスキーマを直して再生成します。

entgql の機能は第 13 章でまとめて扱います。

## 3.8 make gen の正体

では、実際に生成を走らせるのは誰か。入り口は `generate.go` です。

```go
// generate.go
//go:generate go run -mod=mod ./ent/entc.go
//go:generate go run -mod=mod github.com/99designs/gqlgen
```

1. `ent/entc.go` を実行 → ent のコードと `ent.graphqls` を生成
2. gqlgen を実行 → GraphQL サーバーのコードを生成

**順番が大事**です。gqlgen は `ent.graphqls` を読むので、ent の生成が先でなければいけません。

`make gen` は、これを `scripts/gen.sh` 経由で呼び出します。

```makefile
gen: ## ent・gqlgen・mock のうち、前回の生成から
     ## 入力か生成物が変わったものだけを生成する
	sh ./scripts/gen.sh
```

`gen.sh` は、生成の入力と出力のハッシュを `.gen-stamp/` に記録し、**変化がなければ生成を飛ばし**ます。ent の生成は重いので、毎回フルで回さないための工夫です。

| コマンド | 動き |
| --- | --- |
| `make gen` | 変わったものだけ生成 |
| `make gen-all` | 記録を消して全部やり直す |

「生成したはずなのに反映されない」と思ったら `make gen-all` を試してください。

なお、スキーマが 100 を超える規模になると生成はかなりメモリを食います。Docker 上で生成するなら、割り当てメモリに余裕を持たせてください。

## 3.9 既存 DB から取り込む — entimport

ent は「スキーマを書いてから DB を作る」のが基本ですが、**すでに動いている DB に後から ent を導入する**こともできます。

題材アプリも、別フレームワークで運用していた既存 DB を引き継いで Go に移行した、という設定です。その痕跡はスキーマのあちこちに残っています。

- すべてのスキーマが `field.Uint64("id")` を**わざわざ書いている**
- `created_at` / `updated_at` が `Optional()` になっている
- 一部のファイルの先頭に `// Code generated by entimport, DO NOT EDIT.` とある

既存テーブルから ent のスキーマを生成するツールが `entimport` です。

```makefile
dbs: ## ローカル DB のテーブルから ent のスキーマを生成する
	go run ariga.io/entimport/cmd/entimport \
	  -dsn "mysql://..." -tables $$tables
```

取り込んだあとのスキーマは手で編集していくのが普通です。ヘッダの「DO NOT EDIT」は実態に合わなくなるので、気にせず編集して構いません。

### 取り込んだスキーマは「DB の都合」のまま

entimport は DB の列定義を機械的に写すだけです。そのため、**型や名前が DB の都合のまま**残ります。

- 単数形・複数形の変換がおかしい型名（`addresses` テーブルから `Addresse` のような名前ができる）
- 真偽値を整数型の列（例: `bigint` の 0/1）で持っていると、`bool` ではなく整数型のフィールドになる
- 旧フレームワークのタイムスタンプが NULL 許容なので、`Optional()` だらけになる

ent の型を変えると、生成される GraphQL の型も変わります（第 13 章）。また、整数を `bool` に変えると、DB に 0 / 1 以外の値が 1 行でも残っていれば読み込みがエラーになります（第 4 章）。**取り込み直後に「型を整える」作業をどこまでやるか**は、最初に決めておいたほうが後が楽です。

> **現場メモ**
> 取り込みから何年も経ってから、`Int` のまま残っていた真偽値の列を `bool` に揃えたことがあります。DB・ent・ドメインモデルを揃えたうえで、配布済みのアプリを壊さないよう GraphQL の型だけは `Int` のまま残しました（やり方は第 13 章）。取り込み直後に整えていれば不要だった作業です。

### なぜ id を明示するのか

ent の公式ドキュメントによると、`id` フィールドは書かなくても自動で作られ、型は**デフォルトで `int`** です（`doc/md/schema-fields.mdx`）。

一方、取り込み元の DB の主キーは `bigint unsigned` です。初期マイグレーションにもそれが表れています。

```sql
CREATE TABLE `admins` (
  `id` bigint unsigned NOT NULL AUTO_INCREMENT,
  ...
```

ent のデフォルトのままでは型が合いません。そこで、**`bigint unsigned` に対応する `uint64` を明示**しているわけです。新しくスキーマを作るときも、既存に合わせて `field.Uint64("id")` を書きます。

同じように、旧フレームワークのタイムスタンプ列は NULL を許していたため、`created_at` などが `Optional()` になっています。

## 3.10 よく使う開発コマンド

題材アプリで ent に関係する `make` ターゲットをまとめておきます。

| コマンド | 中身 | 用途 |
| --- | --- | --- |
| `make gen` | `scripts/gen.sh` | コード生成 |
| `make add-s m=Foo` | `ent new Foo` | スキーマの雛形作成 |
| `make dis` | `ent describe ./ent/schema` | スキーマの一覧表示 |
| `make dbs tables=...` | `entimport` | DB からスキーマ生成 |
| `make migration name=...` | `ent/migrate/main.go` | マイグレーション生成（第 12 章） |

### make add-s

```
make add-s m=Collection
```

`ent/schema/collection.go` に、`ent.Schema` を埋め込んだ空の struct と `Fields()` / `Edges()` の雛形が作られます。新しいテーブルを足すときの出発点です。

### make dis

```
make dis
```

全スキーマのフィールドとエッジを表形式で出力します。型・Optional・Unique などが一覧で見えるので、**生成コードを読むより早く「このテーブルどうなってたっけ」が分かります**。

### 典型的な作業の流れ

スキーマを変えるときは、この順番になります。

1. `ent/schema/*.go` を編集する
2. `make gen` でコードを再生成する
3. `make migration name=...` で SQL を生成する（第 12 章）
4. 生成されたコードを使って Repository などを書く

---

## まとめ

- 流れは **スキーマを書く → entc で生成 → 生成コードを使う**。生成物は手で編集しない
- `ent/` の中は **`schema/`・`common/`・設定ファイル以外はすべて生成物**
- エンティティごとに **struct・Query・Create・Update・Delete・述語パッケージ**が生成される
- 使う側の主役は **Client（入り口）と Builder（組み立て役）**。**ctx を受け取るメソッドが実行**
- `ent/runtime` は**必ず import** する。忘れると Hook やデフォルト値が登録されず、エラーになる
- 題材アプリは 8 つの**機能フラグ**と **entgql 拡張**を有効にしている。GraphQL スキーマも ent から生成される
- `make gen` は差分判定付きの生成。おかしいときは `make gen-all`
- 既存 DB からは **entimport** でスキーマを取り込める。ただし型は DB の都合のままなので、早めに整える。題材アプリが `id` を `Uint64` で明示しているのもその名残
