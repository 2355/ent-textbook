# 4. フィールド — 列を定義する

> **この章でわかること**
> ent のフィールド型と DB 型の対応。`Optional` と `Nillable` の違いと「ゼロ値問題」。デフォルト値の 2 つの付け方。バリデーション、DB 型の上書き、独自の Go 型の使い方。

スキーマの中でいちばん行数が多いのがフィールド定義です。100 を超えるテーブルを持つ API なら、フィールドは 1,000 を軽く超えます。

ほとんどは `field.String("title")` のような単純な 1 行です。ただ、**`Optional` と `Nillable` の付け方を間違えると、静かにバグが入ります**。この章の山場はそこです。

---

## 4.1 フィールド定義の形

まず全体像です。題材アプリのコレクション（記事をまとめたもの）のスキーマです。

```go
// ent/schema/collection.go
func (Collection) Fields() []ent.Field {
  return []ent.Field{
    field.Uint64("id"),
    field.String("slug").Unique().
      Comment("URL用識別子"),
    field.String("title").Comment("タイトル"),
    field.Text("description").Comment("概要"),
    field.Time("published_at").
      Optional().
      Nillable(),
    field.Time("created_at").
      Optional().
      Default(time.Now),
  }
}
```

Prisma で書くとおおよそこうなります。

```prisma
model Collection {
  id           BigInt    @id @default(autoincrement()) @db.UnsignedBigInt
  slug         String    @unique
  title        String
  description  String    @db.LongText
  published_at DateTime?
  created_at   DateTime? @default(now())
}
```

構造はほぼ同じです。

- `field.型("列名")` で 1 列
- その後ろに `.Optional()` や `.Unique()` を**メソッドチェーンで**つなげて性質を足す

Prisma の `@unique` のような属性が、ent ではメソッド呼び出しになっていると考えてください。

### 列名は snake_case で書く

`field.String("published_at")` のように、**列名は snake_case** で書きます。生成される Go の struct フィールドは自動で `PublishedAt` になります。

## 4.2 型の対応表

よく使う型と、MySQL 上の型の対応です。上から、実務でよく見る順に並べています。

| ent | Go の型 | MySQL |
| --- | --- | --- |
| `Uint64` | `uint64` | `bigint unsigned` |
| `String` | `string` | `varchar(255)` |
| `Time` | `time.Time` | `timestamp` |
| `Text` | `string` | `longtext` |
| `Bool` | `bool` | `boolean` |
| `Int32` | `int32` | `int` |
| `Enum` | 専用の型 | `enum(...)` |
| `Uint32` | `uint32` | `int unsigned` |
| `Uint` | `uint` | `bigint unsigned` |
| `UUID` | 指定した型 | `char(36)` |
| `Uint8` | `uint8` | `tinyint unsigned` |
| `JSON` | 指定した型 | `json` |
| `Int64` | `int64` | `bigint` |
| `Float` | `float64` | `double` |

MySQL 型の対応は ent の `dialect/sql/schema/mysql.go` で決まっています。

### String と Text

TypeScript には `string` しかないので、ここは少し戸惑うところです。

- `field.String` は `varchar(255)`。短い文字列向け
- `field.Text` は `longtext`。長さ無制限

Go 側の型はどちらも `string` です。**違うのは DB の列型だけ**です。タイトルは `String`、本文や説明は `Text` と使い分けます。

### 数値型が細かい

TypeScript の `number` 1 つに対して、Go には `int32` / `uint64` / `float64` などが並びます。

ent では**この Go の型がそのまま列の型を決めます**。`Uint32` なら符号なし 32bit 整数、つまり負の値を入れられない列になります。

題材アプリで `Uint64` が圧倒的に多いのは、ID と外部キーがすべて `bigint unsigned` だからです（次節）。

## 4.3 id を自分で宣言している理由

ent では、`id` フィールドは**書かなくても自動で作られます**。既定は `int` の自動採番です（公式ドキュメント schema-fields「ID Field」）。

それなのに題材アプリのスキーマは、どれも先頭で `field.Uint64("id")` と書いています。

これは題材アプリの歴史に由来します。DB はもともと別フレームワークのアプリが作ったもので、その ID 列は `bigint unsigned` でした。スキーマの多くは、既存 DB から `entimport` というツールで生成されています。

```go
// Code generated by entimport, DO NOT EDIT.
```

という先頭行が、今も多くのスキーマに残っています（その後は手で編集されています）。

**id を `Uint64` で上書きしても、自動採番はそのまま有効です。** 生成された `ent/migrate/schema.go` を見ると、`Increment: true` になっています。

```go
{Name: "id", Type: field.TypeUint64,
  Increment: true},
```

新しいテーブルを作るときも、既存に合わせて `field.Uint64("id")` を書いてください。外部キー列も `Uint64` に揃えます。

> **現場メモ: 逆生成したスキーマは「DB の都合」のまま**
> entimport は DB の列定義から機械的に ent の型を決めます。たとえば「注目記事かどうか」を表すフラグ列が MySQL で整数型（例: `bigint`）だと、ent では `Int` 系のフィールドとして取り込まれ、GraphQL にも `Int` として出ます。意味は真偽値なのに、DB・ent・GraphQL のどこにも bool が出てこない状態です。型名も、テーブル名を単数形にしただけの不自然な名前（例: `addresses` → `Addresse`）が残ることがあります。逆生成したスキーマは「そのまま正しい」と思わず、意味と型が合っているかを一度疑ってください。型を後から揃える手順は 4.8 節のコラムで扱います。

## 4.4 Optional と Nillable

**この章でいちばん大事な節です。**

Prisma では `String?` と書けば「NULL になりうる」が表現でき、TypeScript 側の型も `string | null` になります。**1 つの記号で、DB と言語の両方の性質が決まります。**

ent ではこれが**2 つのメソッドに分かれています**。

| | 意味 | 影響する場所 |
| --- | --- | --- |
| `Optional()` | 作成時に省略してよい | DB（NULL 許容列になる） |
| `Nillable()` | Go の型をポインタにする | Go の struct |

### Optional — DB の話

公式ドキュメントの説明はこうです。

> Optional fields are fields that are not required in the entity creation, and will be set to nullable fields in the database.

つまり `Optional()` を付けると、

- 列が **NULL 許容**になる
- Create のときに**値をセットしなくてもエラーにならない**

逆に言うと、ent のフィールドは**デフォルトで必須**です。何も付けなければ `NOT NULL` で、作成時にセットしないと `Save` がエラーになります。

### Nillable — Go の話

`Nillable()` を付けると、生成される struct のフィールドが**ポインタ型**になります。

記事のスキーマで確認しましょう。

```go
// ent/schema/article.go
field.String("title").Optional(),
field.String("subtitle").
  Optional().
  Nillable(),
```

生成された struct はこうなります。

```go
// ent/article.go（生成物）
Title    string  `json:"title,omitempty"`
Subtitle *string `json:"subtitle,omitempty"`
```

`title` も `subtitle` も DB 上はどちらも NULL 許容です。違うのは**Go で読み出したときの型だけ**です。

### Nillable は Go の型「だけ」を変える

ここは誤解が多いので強調しておきます。`Nillable()` を足しても、

- DB の列定義は変わらない（NULL 許容かどうかは `Optional` が決める）
- マイグレーションは発生しない
- entgql が生成する GraphQL の型も変わらない（`Optional` なら最初から null 可）

変わるのは **Go の struct のフィールド型が `string` から `*string` になる**ことだけです。生成された `ent/migrate/schema.go` を見ると、`Optional` な列には最初から `Nullable: true` が付いています。

つまり「GraphQL では null 可なのに Go では null を表せない」というねじれは、`Optional` だけの列で起こりえます。次の「ゼロ値問題」がその正体です。

### ゼロ値問題

では、DB の `title` が NULL のとき、`Title` には何が入るのでしょうか。

第 2 章で見たとおり、**Go の `string` は nil になれません**。値がなければ「ゼロ値」の `""`（空文字）が入ります。

| DB の値 | `Title`（string） | `Subtitle`（*string） |
| --- | --- | --- |
| `NULL` | `""` | `nil` |
| `''` | `""` | `""` へのポインタ |
| `'abc'` | `"abc"` | `"abc"` へのポインタ |

`Title` だけを見ると、**NULL なのか空文字なのか区別できません**。

数値ならもっと厄介です。`Optional()` だけの `Uint64` 列は、NULL でも `0` でも同じ `0` になります。「未設定」と「0」が区別できなくなります。

TypeScript で言えば、`string | null` だったはずの値を、**勝手に `?? ""` されて受け取っている**ような状態です。

> **現場メモ: GraphQL は null 可なのに 0 が返ってくる**
> 「カテゴリ ID（`Optional()` のみの `Uint64`）が未設定なら null を返す」はずの GraphQL フィールドが、実際には `0` を返していたことがあります。GraphQL のスキーマは null を許しているのに、Go の struct が `uint64` なので、NULL がゼロ値の `0` に化けてそのまま返っていたのです。直し方は 2 つあります。スキーマに `Nillable()` を足して `*uint64` にするか、画面側で `0` を「未設定」として扱うかです。前者は Go の型が変わるので、そのフィールドを使う箇所すべてに影響が広がります。影響範囲を見てから選んでください。

### どちらを使うか

判断基準は 1 つです。

> **NULL に意味があるなら `Optional().Nillable()`。NULL とゼロ値を同一視してよいなら `Optional()` だけ。**

コレクションの `published_at` が良い例です。

```go
field.Time("published_at").
  Optional().
  Nillable().
  Comment("公開日時。NULL=下書き、" +
    "未来日=公開予約中、過去日=公開中"),
```

ここでは **NULL が「下書き」という意味を持っています**。`Nillable()` がないと、NULL は `time.Time` のゼロ値（西暦 1 年 1 月 1 日）になります。「過去日=公開中」と判定されてしまいます。

**Optional だけの列では、NULL とゼロ値が区別されずに扱われます。** ただし entimport で機械的に取り込まれた列も多いので（4.3 節）、意図して選ばれたとは限りません。NULL に意味がある列でないかは、コメントや用途で確認してください。

### Optional なしの Nillable

公式ドキュメントには、`Optional` を付けずに `Nillable` だけを使う例も載っています（「Nillable required fields」）。列は NOT NULL のまま、Go の型だけポインタにする使い方です。

`Select` で一部の列だけ取得したとき、取得しなかった列が `nil` になるので区別できます。題材アプリではこの用法は使っておらず、Nillable はすべて `Optional().Nillable()` の組み合わせです。

## 4.5 Optional・Default が生むメソッド

`Optional` と `Nillable` は、生成される Builder のメソッドにも影響します。

```go
// 作成時: ポインタを受け取るセッター
func (c *ArticleCreate) SetNillableTitle(
  s *string) *ArticleCreate

// 更新時: NULL に戻すメソッド
func (u *ArticleUpdate) ClearTitle()
  *ArticleUpdate
```

- **`SetNillableXxx`**: 引数のポインタが `nil` なら何もしない、値があればセットする。GraphQL の任意入力をそのまま渡すときに便利です。Create では `Optional` か `Default` を持つフィールドに、Update では `UpdateDefault` 以外の全フィールドに生成されます
- **`ClearXxx`**: 列を NULL にする。`Optional` な列にだけ生成されます

`ClearXxx` が生えているかどうかで、「この列は NULL にできるのか」がコード補完から分かります。Builder の詳細は第 8 章で扱います。

「画面で空文字を入力されたら NULL として保存したい」ときは、Resolver で空文字を `nil` に直し、Repository で `SetNillableXxx`（作成時）や `ClearXxx`（更新時）に振り分ける、という流れになります。`Nillable` を足さなくても、書き込み側は NULL を扱えます。

## 4.6 デフォルト値

デフォルト値の付け方は 2 系統あります。

### ent 側で入れる: Default / UpdateDefault

```go
field.Time("created_at").
  Optional().
  Default(time.Now),
field.Time("updated_at").
  Optional().
  Default(time.Now).
  UpdateDefault(time.Now),
```

- `Default`: 作成時に値がセットされていなければ、ent が入れる
- `UpdateDefault`: 更新のたびに ent が入れる

`time.Now` のように**関数を渡すと、Go のコードが値を作って INSERT 文に含めます**。DB の列定義に `DEFAULT` は付きません。

一方、`Default("draft")` や `Default(0)` のような**固定値（数値・bool・文字列・enum）を渡すと、ent が値を入れることに加えて、列定義にも `DEFAULT` が付きます**（`entc/gen/type.go`）。

`created_at` と `updated_at` のこの組み合わせは、役割としては Prisma の `@default(now())` と `@updatedAt` に当たります。ただし仕組みは少し違います。

- Prisma の `@default(now())` は、MySQL では DDL の `DEFAULT CURRENT_TIMESTAMP(3)` になる（DB 側）
- ent の `Default(time.Now)` は Go 側で値を作る
- Prisma の `@updatedAt` は Prisma Client が値を入れる（DB の `ON UPDATE` ではない）。ent の `UpdateDefault` と同じく ORM 側の仕組み

題材アプリでは `UpdateDefault` はすべて `updated_at` に付いています。

`Optional().Default(...)` という組み合わせが多いのは、既存 DB の列が NULL 許容だったためです。ent 経由で作る限り値は入ります。

### 関数を渡すか、値を渡すか

`time.Now` と `time.Now()` は別物です。

- `time.Now` — **関数そのもの**。作成のたびに呼ばれる
- `time.Now()` — 関数を**呼んだ結果の値**

`Time` の `Default` は引数の型が緩いため、`time.Now()` を渡してもコンパイルが通ってしまいます。すると**プロセス起動時に 1 回だけ評価された時刻**が、すべてのレコードに入ります。

ent の生成テンプレート（`entc/gen/template/runtime.tmpl`）を見ると、関数でない値はそのまま固定値として扱われます。題材アプリにはこの事故の跡がコメントで残っています。

```go
// ent/schema/like.go
field.Time("created_at").
  // NOTE: time.Now()で指定すると一定期間同じ値で
  // 登録されたためMySQLのDefaultを使用
  Optional().
  Annotations(
    entsql.Default("CURRENT_TIMESTAMP"),
  ),
```

### DB 側で入れる: entsql.Default

上の例の `entsql.Default("CURRENT_TIMESTAMP")` が 2 つ目の方式です。

これは**列定義そのものに `DEFAULT CURRENT_TIMESTAMP` を付けます**。ent が値を入れなくても、DB が埋めます。

| | Default（関数） | Default（固定値） | entsql.Default |
| --- | --- | --- | --- |
| 値を作る | Go | Go と DB | DB |
| DDL の DEFAULT | なし | あり | あり |
| ent 以外の INSERT | 効かない | 効く | 効く |

### ユニーク列のデフォルト

公式ドキュメントには「Default は **Non-unique** なフィールドで使える」とあります。ただしこれは固定値の話です。

ent のコード生成（`entc/gen/type.go`）は「ユニーク かつ デフォルトが関数でない」場合だけをエラーにします。**関数なら `Unique` と併用できます。** UUID 列がその例です（4.10 節）。

### Enum のデフォルト

Enum のデフォルトは文字列で指定します。

```go
// ent/schema/article.go
field.Enum("status").Values(
  "draft",     // 下書き
  "published", // 公開中
  "archived",  // アーカイブ
).
  Default("draft"),
```

## 4.7 Unique と Comment

### Unique

`.Unique()` を付けると、列にユニーク制約が張られます。

```go
field.String("slug").Unique(),
```

**単一列のユニーク**だけはここで書けます。「`user_id` と `article_id` の組でユニーク」のような複合ユニークは、インデックスとして別に書きます（第 6 章）。

### Comment

`.Comment("...")` は、生成される Go の struct フィールドのコメントになります。大きなスキーマでは、**スキーマを読むときの最大の手がかり**です。積極的に書きましょう。

既定では DB の列コメントにはなりません。スキーマに `entsql.WithComments(true)` を付けると、DB の列コメントにも書き込まれます（第 6 章）。

## 4.8 Enum

`field.Enum` は、許される値の一覧を持つフィールドです。

```go
// ent/schema/subscription.go
field.Enum("status").
  Values("active", "past_due", "unpaid",
    "canceled", "trialing"),
```

Prisma の `enum` に相当します。ent はフィールドごとに専用の型と定数を生成します。

```go
// ent/article/article.go（生成物）
StatusDraft Status = "draft"
// ...
func StatusValidator(s Status) error
```

- DB 上は MySQL の `enum(...)` 列になる
- Go 上は `article.StatusDraft` のような**定数で扱える**
- 一覧にない値を入れようとすると、`Save` の前に**バリデーションエラー**になる

値を追加するとマイグレーション（第 12 章）で列定義が変わる点は、Prisma の enum と同じです。

> **現場メモ: 列を bool に変えるなら、先にデータを確かめる**
> 4.3 節のコラムで触れた「真偽値なのに整数型 + `Int`」の列を、ent の `Bool` に揃えたことがあります。このとき注意が要るのは**既存データ**です。
>
> ent は `Bool` 列を `sql.NullBool` で読み込みます（`entc/gen/type.go`）。その中身は Go 標準の `database/sql` の変換で、`0` / `1` 以外の数値は `couldn't convert 3 into type bool` のようなエラーになります（`database/sql/driver/types.go`）。
>
> このエラーは行単位でスキップされず、`All` などの**クエリ全体のエラー**として返ります。つまり **0 / 1 以外の値が 1 行でも残っていると、その行を含む一覧の取得がまるごと失敗します**。
>
> 型を変えるマイグレーションの前に `WHERE col NOT IN (0, 1)` のような SQL で該当行がないことを確かめ、あれば先に直す。これをリリースの前提条件として明記しておくのが安全です。確認は DDL の適用前だけでなく、**ent の型を変えたアプリのリリース前**にも必要です。読み込みエラーはアプリ側で起きるからです。GraphQL の型を変えずに ent 側だけ bool にする方法は第 13 章で扱います。

## 4.9 型を細かく調整する

ここからは使用頻度は低いものの、実務で出てくる機能です。

### MaxLen — 長さ制限

```go
// ent/schema/push_subscription.go
field.String("endpoint").MaxLen(500).Unique(),
```

`MaxLen` は 2 つのことを同時にします（`schema/field/field.go`）。

- 列を `varchar(500)` にする
- `len(v) > 500` ならエラーにするバリデータを足す

注意点として、Go の `len` は**バイト数**を数えます。日本語 1 文字は UTF-8 で 3 バイトなので、文字数の制限としては使えません。

### Validate — 独自のバリデーション

文字数で制限したい列では、`Validate` で自作します。

```go
// ent/schema/comment.go
field.Text("body").
  Validate(func(s string) error {
    // maxLenだとマルチバイト文字が考慮されて
    // いないため、runeで文字数をカウント
    if len([]rune(s)) > 9999 {
      return fmt.Errorf("...")
    }
    return nil
  }),
```

`Validate` に渡した関数は、**Create / Update の保存前**に実行されます。エラーを返すと保存されません。zod のスキーマを ORM に埋め込んでいるようなものです。

ただし、ここに書くのは**列単体で判定できる制約だけ**にしてください。「他の列との組み合わせ」や「DB を引かないと分からない条件」はここでは書けません。

### SchemaType — DB 型を上書きする

ent の既定の型が合わないときは、方言ごとに DB 型を指定できます。

```go
// ent/schema/collection.go
field.Time("published_at").
  SchemaType(map[string]string{
    dialect.MySQL: "datetime",
  }).
  Optional().
  Nillable(),
```

`field.Time` の既定は `timestamp` です。MySQL の `timestamp` は扱える範囲が 2038 年までで、タイムゾーン変換の挙動も `datetime` と異なります。公開日時のような列には `datetime` を指定するのが無難です。

ほかにも次のような使い方があります。

- 生年月日を `String` で扱いつつ、列は `date` にする
- `Text` だが、列は `longtext` ではなく `text` にする

**Go の型は変わらず、DB の型だけが変わります。**

### GoType — Go の型を差し替える

逆に、DB の型はそのままで **Go の型を独自の型にする**のが `GoType` です。

```go
// ent/schema/user.go
field.Uint8("prefecture").
  GoType(prefecture.Prefecture(0)).
  Validate(func(ui uint8) error {
    p := prefecture.Prefecture(ui)
    if p >= prefecture.Hokkaido &&
      p <= prefecture.Okinawa {
      return nil
    }
    return errors.New("invalid value")
  }),
```

`prefecture.Prefecture` は、アプリ側で `type Prefecture uint8` と定義した型です。

生成された struct は `Prefecture prefecture.Prefecture` になります。ただの `uint8` ではなく**ドメインの型として扱える**わけです。TypeScript の branded type に近い発想です。

公式ドキュメントによると、`GoType` に渡す型は「基本型に変換できる型」か「`ValueScanner` を実装した型」である必要があります。`Prefecture` は前者です。

## 4.10 UUID と JSON

### UUID

```go
// ent/schema/article.go
field.UUID("uuid", uuid.UUID{}).
  Unique().
  Default(uuid.New),
```

- 第 2 引数で**Go の UUID 型**を指定する
- `Default` には「UUID を返す関数」を渡す

4.6 節で見たとおり、関数なので `Unique` と併用できます。

外部に見せる識別子（URL など）に連番の `id` を使わず、`uuid` 列や `slug` 列を別に持つのはよくあるパターンです。

### JSON

```go
// ent/schema/article.go
field.JSON("metadata", json.RawMessage{}).
  Optional(),
```

第 2 引数は Go 側の型です。ここでは `json.RawMessage`（JSON のバイト列そのもの）を指定しています。中身の構造を ent に教えず、**読み書きする側で解釈する**という選択です。

`[]string{}` や独自の struct を渡せば、ent が自動で JSON とのエンコード・デコードをします。

## まとめ

- フィールドは `field.型("snake_case名")` に**メソッドチェーンで性質を足す**
- `String` は `varchar(255)`、`Text` は `longtext`。Go の型はどちらも `string`
- 題材アプリの `id` と外部キーは **`Uint64`**。既存 DB を引き継いでいるため。逆生成したスキーマは型が「DB の都合」のまま残りやすい
- **`Optional` は DB の話（NULL 許容・作成時に省略可）、`Nillable` は Go の話（ポインタ型）**。Nillable を足しても DB と GraphQL の型は変わらない
- Optional だけだと NULL は**ゼロ値**（`""`, `0`, 西暦 1 年）になる。NULL に意味があるなら `Nillable` も付ける
- `Default(time.Now)` は ent が値を作る。`time.Now()` と書くと**値が固定される**
- `entsql.Default` や固定値の `Default` は DB の列定義に DEFAULT を付ける
- `MaxLen` は**バイト数**。文字数制限は `Validate` で書く
- `SchemaType` は DB の型だけ、`GoType` は Go の型だけを差し替える
- 列を `Bool` に変えるときは、**0 / 1 以外の値が残っていないか先に確かめる**
